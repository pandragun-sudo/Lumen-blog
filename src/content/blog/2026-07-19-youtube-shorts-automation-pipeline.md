처음에는 간단할 거라고 생각했습니다.  
"유튜브 API로 데이터 가져오고, DB에 저장하고, 화면에 보여주면 끝 아닌가?"  
6개월 뒤, 저는 `cronJobs.js` 파일을 수십 번 뜯어고치고, API 쿼터를 세 번 소진하고, 한 번은 밤새 서버가 죽어있는 것을 아침에 발견하는 경험을 한 뒤에야 깨달았습니다.  
자동화는 구현하는 것이 아니라 **설계하는 것**이라는 사실을.  

## 자동화가 필요한 진짜 이유

1MIN DRAMA 채널을 운영하면서 가장 힘든 것은 영상 제작이 아니었습니다.  
**"요즘 어떤 주제가 뜨는지"를 파악하는 반복 작업**이었습니다.  

경쟁 채널 20개를 매일 직접 방문해서 최신 영상을 확인하고, 조회수가 급증한 영상을 노션에 정리하고, 그것을 바탕으로 다음 주 업로드 계획을 세우는 데 하루 평균 2시간이 걸렸습니다.  
주 5일 기준 월 40시간, 연간 480시간.  
이것은 그냥 낭비가 아니라, 제가 콘텐츠 기획에 쓸 수 있는 시간을 빼앗아가는 **기회비용의 도둑**이었습니다.  

자동화의 목표는 이 2시간을 0으로 만드는 것이었습니다.  

## Lumen Insights 자동화 파이프라인의 전체 구조

결과적으로 완성된 파이프라인은 다음과 같은 구조입니다.  

```
[새벽 4시] 데이터 수집 레이어
  ↓ YouTube Data API v3 (quota: ~3,000 units/day)
  ↓ 채널별 최신 영상, 조회수, 좋아요 수, 댓글 수 수집
  ↓ PostgreSQL DB에 스냅샷 저장

[새벽 5시] 분석 레이어  
  ↓ 전날 스냅샷 vs 오늘 스냅샷 비교 (Delta 계산)
  ↓ 24시간 조회수 증가율 상위 영상 추출
  ↓ 키워드 빈도 분석 및 트렌드 점수 계산

[아침 8시] 발행 레이어
  ↓ Gemini AI → 트렌드 데이터 기반 블로그 원고 생성
  ↓ GitHub REST API → Lumen-blog 저장소에 자동 커밋
  ↓ Cloudflare Pages CI/CD → 자동 배포
  ↓ Telegram Bot → 대표에게 완료 보고
```

이 파이프라인이 작동하는 날이면 저는 아침 커피를 마시며 텔레그램 메시지를 확인하는 것이 전부입니다.  
"오늘 블로그 포스팅 완료: '이번 주 드라마 쇼츠 급상승 채널 Top5' 배포 성공 ✓"  

## 세 번 실패한 설계와 교훈

## 1차 실패: YouTube API 쿼터 폭탄과 search.list

첫 버전은 모든 채널의 데이터를 매시간 수집하는 방식이었습니다.  
이틀 만에 YouTube API 일일 할당량 10,000 units가 소진되었습니다.  
YouTube API의 과금 구조를 제대로 파악하지 않은 채 설계를 시작한 것이 실수였습니다.  

| API 엔드포인트 | 소모 Units | 비고 |
|---|---|---|
| `videos.list` | 1 unit | 영상 기본 정보 |
| `channels.list` | 1 unit | 채널 정보 |
| `search.list` | 100 units | 검색 결과 |
| `commentThreads.list` | 1 unit | 댓글 수집 |

`search.list`가 100 units라는 사실을 뒤늦게 발견했을 때, 이미 하루 할당량의 30%가 검색 호출로 소진된 뒤였습니다.  
해결책: `search.list` 호출을 최소화하고, 한 번 파악한 채널 ID를 DB에 저장하여 재사용하는 방식으로 전환했습니다.  

## 2차 실패: 호출부 누락으로 발생한 좀비 크론잡

두 번째 버전에서는 `cronJobs.js`에 스케줄러를 등록했는데, 어느 날부터 텔레그램 보고가 오지 않는 것을 발견했습니다.  
확인해보니 크론잡 함수는 `require`로 불러왔지만, 실제 `startCronJobs()` 호출부를 추가하는 것을 잊어버렸습니다.  
코드는 존재했지만 한 번도 실행된 적이 없는 **좀비 크론잡**이었습니다.  
2주 동안 데이터 수집이 중단된 상태를 전혀 몰랐습니다.  

해결책: 크론잡이 실행될 때마다, 그리고 특히 오류 없이 완료될 때 텔레그램으로 알림을 보내는 헬스체크 로직을 의무화했습니다.  
조용히 실패하는 시스템은 작동하지 않는 시스템보다 더 위험합니다.  

## 3차 실패: Gemini API Rate Limit과 429 에러

블로그 자동 발행이 메인 앱의 '키워드 분석' 기능과 동일한 Gemini API 키를 공유하고 있었습니다.  
블로그 포스팅이 새벽에 대량으로 생성되면서 낮 시간대의 메인 앱 기능이 "429 Too Many Requests" 오류로 마비되는 사태가 발생했습니다.  

해결책: 블로그 자동화 스케줄러를 백엔드 크론잡에서 분리하여 AI 에이전트가 직접 처리하도록 전환했습니다.  
에이전트는 자체 모델 파워를 사용하기 때문에 서버의 API 쿼터를 전혀 소모하지 않습니다.  

## 자동화를 설계할 때 반드시 물어봐야 할 3가지

이 세 번의 실패를 겪고 나서, 저는 새로운 자동화를 설계할 때 반드시 다음 세 가지를 먼저 확인합니다.  

**Q1. 이 시스템이 실패했을 때 나는 어떻게 알 수 있는가?**  
알림이 없는 자동화는 없는 것과 같습니다. 모든 크론잡에 성공/실패 알림을 달아야 합니다.  

**Q2. 이 시스템이 공유하는 외부 자원(API, DB)의 한계는 무엇인가?**  
API 쿼터, DB 연결 수, 서버 메모리 — 모든 외부 의존성의 한계를 미리 파악하고 설계에 반영해야 합니다.  

**Q3. 이 자동화가 다른 기능에 영향을 주지는 않는가?**  
자동화는 서로 격리되어야 합니다. 한 파이프라인의 과부하가 다른 기능을 마비시켜서는 안 됩니다.

여전히 완벽하지 않지만, 매일 조금씩 더 안정적인 시스템으로 성장하고 있습니다.  
자동화는 목적지가 아니라 끝없이 개선하는 여정입니다.
