## 지우면 끝날 줄 알았던 치명적인 실수

"앗, 잘못 올렸네."
터미널에서 `git push`를 누른 직후, 올라가면 안 되는 파일이 포함되었다는 걸 깨닫는 순간이 있습니다. 식은땀이 흐르지만, 재빨리 해당 파일을 삭제하고 다시 커밋해서 푸시하면 문제가 해결될 거라고 생각하기 쉽습니다.

하지만 GitHub와 같은 버전 관리 시스템은 '수정 이력'을 영구적으로 보관합니다. 최신 코드에서 파일이 지워졌더라도, 커밋 히스토리를 뒤지면 누구나 과거의 파일을 다운로드할 수 있습니다. 이것이 1인 개발자들이 가장 빈번하게 저지르면서도 가장 파장이 큰 보안 사고의 시작입니다.

## 아찔했던 2026년 8월의 데이터 노출 사고

실제로 루멘 인사이트 프로젝트를 진행하면서 뼈아픈 사고를 겪었습니다.
편의를 위해 로컬에 백업해 두었던 데이터베이스 덤프 파일(`aiven_dump.sql`, 83MB)과 소스코드 압축 파일(`yt-shorts-mvp-source.zip`, 101MB)이 `.gitignore` 필터링을 누락한 채 `main` 저장소에 그대로 커밋되어 버린 것입니다.

단순한 용량 낭비가 아니었습니다. 이 압축 파일과 덤프 파일 내부에는 서비스 초기 이용자들의 이메일, 전화번호, 생년월일은 물론, 암호화되지 않은 평문 상태의 YouTube OAuth 액세스 토큰 5건과 리프레시 토큰 1건, `session` 테이블 전체 데이터, 그리고 운영 서버의 API 키가 들어있는 `.env` 파일까지 모두 포함되어 있었습니다.

이 데이터가 악용되었다면 사용자의 유튜브 채널 권한이 탈취될 수도 있는, 말 그대로 최악의 시나리오였습니다. 혼자서 모든 것을 개발하고 관리하다 보니 '기능 구현'에만 매몰되어, 배포 과정의 가장 기본적인 '비밀 정보 검사'를 간과한 대가였습니다.

## 사고 수습의 과정과 깨달음

다행히 피해가 발생하기 전에 조치를 취할 수 있었지만, 사고 수습 과정은 험난했습니다.
단순히 파일을 지우고 새로 커밋하는 것으로는 이력을 지울 수 없기 때문에, `git filter-branch`와 BFG Repo Cleaner 같은 도구를 사용해 깃 저장소의 전체 히스토리에서 해당 파일들의 흔적을 영구 삭제해야 했습니다.
또한, 이미 한 번이라도 노출된 API 키와 OAuth 토큰은 즉시 폐기(Revoke)하고 새롭게 재발급을 받아야만 했습니다.

이 사건을 통해 1인 개발 체제에서 반드시 지켜야 할 몇 가지 절대적인 보안 규약을 세우게 되었습니다.

첫째, 어떠한 이유로든 `.env` 파일과 시스템 환경변수 파일, `*.sql` 및 `*.dump` 같은 데이터베이스 백업 파일은 Git 트래킹 대상에서 제외해야 합니다.
둘째, 인증서나 개인키(`*.pem`, `*.key`), 그리고 확인되지 않은 10MB 이상의 대용량 파일은 아예 작업 폴더 내에 두지 않고 별도의 로컬/클라우드 스토리지에 분리 보관해야 합니다.
셋째, 사용자 이메일, 전화번호, OAuth 토큰 등 민감한 정보는 데이터베이스 저장 단계부터 무조건 암호화(예: `cryptoHelper.encrypt()`)를 거쳐야 하며, 암호화 키는 절대 재생성되지 않도록 안전하게 분리 관리해야 합니다.

## 자동화된 안전장치의 필요성

사람은 반드시 실수를 합니다. "다음부터는 조심해야지"라는 다짐은 보안 대책이 될 수 없습니다.
이 사고 이후, 코드를 푸시하기 전에 깃허브 저장소에 올라가는 파일 목록 중 민감한 확장자나 용량이 큰 파일이 포함되어 있는지 자동으로 스캔하는 스크립트(Auto Push Skill)를 도입했습니다.

1인 창업가에게 보안은 '시간이 남을 때 챙기는 옵션'이 아니라, '서비스의 생사를 결정짓는 기본 전제'입니다. 개발 속도가 하루 이틀 늦어지더라도, 민감한 데이터가 포함된 커밋을 사전에 차단하는 안전장치를 구축하는 것이 장기적으로 서비스를 지키는 유일한 방법입니다.
