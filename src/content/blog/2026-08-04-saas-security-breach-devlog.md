## 프라이빗(Private) 저장소의 함정

솔로 창업자로서 SaaS를 개발하다 보면, 코드를 올리는 깃허브(GitHub) 저장소가 비공개(Private)라는 이유만으로 보안에 무감각해지기 쉽습니다.  
본 블로그에서 직접 운영 중인 [Lumen Insights](https://app.lumeninsights.kr/?utm_source=lumen_blog&utm_medium=blog_post&utm_campaign=auto_generated_post) 역시 V2 런칭을 앞두고 다크 모드 UI와 매끄러운 사용자 경험을 만드는 데만 집착했습니다.  
저장소가 비공개니 아무도 못 본다는 생각에, 정작 서비스의 심장인 **백엔드 인프라와 크리덴셜 관리**에는 소홀했던 것입니다.  
이번 V2 런칭 전, 외부 개발자를 초빙하여 내부 코드 리뷰와 보안 감사(Audit)를 진행하면서 아찔한 사실을 발견했습니다.  
과거 로컬 환경에서 작업하던 중 데이터베이스 백업 파일(`aiven_dump.sql`)과 100MB짜리 프로젝트 압축 파일이 실수로 `.gitignore` 필터링을 빠져나가 저장소 이력에 남아있었던 것입니다.  
아무리 비공개 저장소라도, 향후 팀원이 추가되거나 외주 개발자와 협업할 때 유튜브와 구글 클라우드 <span style="color: #ef4444;">API 마스터키</span>가 평문으로 노출될 수 있는 잠재적 위험 상태였습니다.  

## 선제적 방어: 내부 위생 점검과 즉각적인 롤백

외부의 해킹 위협은 없었지만, 내부 보안 위생(Hygiene)을 완벽하게 다지기 위해 발견 즉시 대대적인 방어 조치에 돌입했습니다.  
만약 이 상태로 외부 협업이 진행되거나 훗날 코드가 오픈소스로 전환되었다면 어땠을까요?  
누군가 제 구글 계정의 **API 과금 폭탄**을 유발하거나, 수파베이스(Supabase) 데이터베이스에 직접 접속하는 불상사가 생길 뻔했습니다.  
저는 조금의 찝찝함도 남기지 않기 위해 깃허브 토큰을 선제적으로 폐기하고 데이터베이스 비밀번호를 강제 리셋했습니다.  
또한 모든 구글 API 키에 <span style="color: #2563eb;">API 종류 제한</span>을 걸어 완전히 새로운 자물쇠로 튼튼하게 교체했습니다.  
이번 경험은 그 어떤 화려한 기능보다, 기본 중의 기본인 **환경변수(.env) 분리**가 혼자 일할 때부터 체화되어야 할 가장 중요한 습관이라는 것을 가르쳐 주었습니다.  

## 솔로 창업자를 위한 실전 보안 체크리스트

나 혼자 보는 비공개 코드라도, 코드를 짜기 전에 반드시 **저장소 위생 상태**를 점검하는 습관을 들여야 합니다.  
가장 먼저 프로젝트 최상단에 있는 `.gitignore` 파일에 `.env`와 `.sql`, 그리고 `*.zip` 같은 데이터 덤프 파일이 확실하게 등록되어 있는지 두 번, 세 번 확인하십시오.  
또한 로컬 환경에서 사용하는 환경변수와 실제 운영(Production) 서버의 환경변수를 철저하게 분리해야 합니다.  
특히 배포 서버에서는 데이터베이스 접속 비밀번호나 암호화 키를 코드 내부에 하드코딩하지 말고, 반드시 배포 플랫폼(Render, Vercel 등)의 **안전한 환경변수 설정창**을 통해서만 주입해야 합니다.  
혹시라도 저장소에 키가 올라갔다면 "비공개니까 괜찮겠지" 하고 방치하지 마시고, 즉시 사용 중인 외부 서비스 대시보드로 달려가 기존 토큰을 **Revoke(폐기)** 하는 것이 가장 깔끔한 해결책입니다.  
Lumen Insights는 V2 런칭 전 꼼꼼한 내부 감사를 거치며 인프라 레벨의 방어벽을 단단히 굳혔고, 이제 더욱 안전하고 신뢰할 수 있는 플랫폼으로 도약할 준비를 마쳤습니다.
