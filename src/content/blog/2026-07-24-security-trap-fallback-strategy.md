구글 OAuth 로그인이 모든 사용자 환경에서 벽돌로 변했다. V2 런칭을 코앞에 두고 터진 이 사태의 원인을 찾는 데 4시간을 태웠다. 
서버 로그와 브라우저 콘솔을 쥐어짜듯 뒤진 끝에 찾아낸 범인은, 며칠 전 보안 감사랍시고 우겨넣은 `SameSite=Strict` 쿠키 설정이었다. 

보안을 최대로 끌어올리겠다는 얄팍한 결정이 리다이렉트 흐름을 완전히 박살냈다. 구글 로그인 후 accounts.google.com에서 우리 도메인으로 넘어오는 찰나의 순간, 브라우저는 이걸 크로스 도메인 탐색으로 간주해버렸다. Strict 설정은 이 과정에서 OAuth state 값을 담은 세션 쿠키를 무자비하게 차단했다. 
서버는 state 값을 받지 못하니 인증을 거부하고 유저를 로그인 창으로 내동댕이쳤다. 

설정을 `SameSite=Lax`로 되돌리는 순간 허탈하게 문제가 사라졌다. 최상위 탐색에서 쿠키 전송을 허용하는 Lax가 왜 사실상의 표준으로 쓰이는지 뼈저리게 확인한 셈이다. 

이 사건은 시스템의 단일 장애점이 얼마나 취약한지 까발려줬다. 보안 패치 하나가 핵심 퍼널을 끊어버리는 촌극을 막으려면 결국 폴백 방어선을 겹겹이 쳐야 한다. 
구글 로그인이 터지면 즉각 이메일 로그인 우회로를 띄운다. YouTube API 쿼터가 증발하면 DB 캐시 데이터를 꺼내오고, 그마저 없으면 수집 중이라는 텍스트를 노출시켜 무한 로딩의 수렁을 피한다. 데이터베이스가 뻗으면 읽기 전용 캐시에서 마지막 데이터를 뱉어내게 만들었다. 

조용히 실패하는 시스템이 가장 악질이다. 백그라운드에서 무슨 난리가 나든 화면 앞의 유저는 상황을 인지해야 한다. 무작정 보안을 강화한다는 핑계가 핵심 사용자 여정을 부숴버릴 수 있다는 트레이드오프를 머리에 박아둬야 한다.
