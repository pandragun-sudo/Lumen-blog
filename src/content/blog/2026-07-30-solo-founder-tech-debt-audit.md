본 블로그에서 직접 운영 중인 [루멘 인사이트(Lumen Insights)](https://lumeninsights.kr/?utm_source=lumen_blog&utm_medium=blog_post&utm_campaign=auto_generated_post)의 V2 업데이트를 진행하면서, 가장 뼈저리게 느낀 점이 하나 있습니다.  
바로 기능 개발의 속도만큼이나, 뒤에 남겨진 **기술 부채(Technical Debt)**를 주기적으로 청산하는 과정이 서비스의 생존과 직결된다는 사실이었습니다.  
1인 창업가(솔로프리너)나 소규모 팀은 한정된 리소스로 빠르게 MVP(최소 기능 제품)를 시장에 내놓는 데 집중합니다.  
하지만 초기 단계에서 타협했던 코드 구조나 보안 설정, 메모리 관리 이슈들은 어느 순간 서비스의 발목을 잡는 거대한 장벽으로 돌아오곤 합니다.  
오늘은 루멘 인사이트 V2 개발 과정에서 진행한 체계적인 기술 감사(Audit) 기록을 바탕으로, 숨겨진 기술 부채를 찾아내고 해결하는 실질적인 생존 전략을 공유하고자 합니다.

## 빠르게 달리기 위해 반드시 필요한 '기술 감사(Audit)'

루멘 인사이트는 유튜버와 마케터들을 위한 데이터 분석 기능을 빠르게 확장해오고 있습니다.  
이 과정에서 AI 기반 편의성 도구(키워드 추출, 썸네일 분석, 대본 요약 등)와 같은 가벼운 유틸리티 기능들을 기획하며, 시스템의 복잡도는 자연스럽게 증가했습니다.  
새로운 미니 툴들은 검색 엔진 최적화(SEO) 트래픽을 대량으로 끌어오는 훌륭한 **미끼(Lead Magnet)** 역할을 하지만, 동시에 서버 자원과 유지보수 비용을 가중시킵니다.  
이러한 상황에서 기능 추가에만 몰두한다면, 예기치 못한 서버 다운이나 데이터 유출과 같은 치명적인 문제에 직면할 수밖에 없습니다.  
따라서 저는 잠시 기능 개발을 멈추고, 백엔드와 프론트엔드 전반에 걸친 보안, 성능, 유지보수 이슈를 점검하는 오디팅(Auditing)을 단행했습니다.

## V2 개발 감사에서 발견한 핵심 기술 부채와 해결책

이번 감사 과정에서 발견된 주요 이슈들은 대부분 눈에 띄지 않지만 서비스의 근간을 흔들 수 있는 잠재적 위협들이었습니다.  
다음은 실제 해결한 핵심 과제들과 그 구체적인 조치 내용입니다.

**첫째, API 보안의 가장 기본, CORS와 세션 설정 강화입니다.**  
초기 개발 편의를 위해 설정해두었던 CORS 와일드카드(`*`)는 운영 환경에서 심각한 보안 취약점이 될 수 있습니다.  
이를 명시적인 origin으로 변경하고 `credentials: true` 설정을 적용하여, 허용된 도메인에서만 인증된 요청이 가능하도록 보안을 대폭 강화했습니다.  
또한, 서버 세션 쿠키에 `sameSite` 속성을 추가하여 CSRF(교차 사이트 요청 위조) 공격의 위험을 원천적으로 차단했습니다.

**둘째, 사용자 경험과 권한 분리를 위한 서버사이드 가드 구축입니다.**  
프론트엔드 로직에만 의존하는 권한 체크는 한계가 명확합니다.  
V2에서는 `middleware.ts`를 새롭게 도입하여, 관리자나 유료 사용자 전용 페이지에 대한 접근을 서버 단에서부터 원천적으로 통제하도록 수정했습니다.  
이를 통해 클라이언트 측 렌더링이 완료되기 전에 미인가 사용자를 안전하게 리다이렉트 시킬 수 있었습니다.

**셋째, 눈에 보이지 않는 메모리 누수와 좀비 프로세스 차단입니다.**  
프론트엔드의 커스텀 훅에서 `useEffect`의 정리(cleanup) 함수가 누락되면, 컴포넌트가 언마운트된 후에도 이벤트 리스너가 남아 메모리 누수(Memory Leak)를 유발합니다.  
이를 꼼꼼히 찾아내어 제거했으며, 서버 구동 스크립트에는 `trap EXIT` 구문을 추가하여 프로세스 종료 시 백그라운드 프로세스가 **좀비 상태**로 남지 않도록 안정성을 확보했습니다.

## 지속 가능한 성장을 위한 실질적인 제언

이러한 기술 부채 해결 과정은 단순히 '코드를 예쁘게 만드는 것'이 아닙니다.  
이는 트래픽이 폭주하거나 예상치 못한 악의적 접근이 발생했을 때, 서비스가 다운되지 않고 유연하게 버틸 수 있는 <span style="color: #2563eb;">기초 체력</span>을 기르는 일입니다.  
또한, 사용되지 않는 데드코드를 제거하고, 중복 호출되던 데이터 페칭 로직을 단일화함으로써 유지보수의 복잡성을 크게 낮출 수 있었습니다.  

1인 개발자나 소규모 팀일수록 기능 확장의 유혹을 잠시 내려놓고, 주기적인 코드 감사 주간(Audit Week)을 가지는 것을 강력히 추천합니다.  
현재 작성 중인 코드의 한 줄이, 미래의 나에게 갚아야 할 이자가 될지 아니면 든든한 자산이 될지는 바로 이러한 체계적인 점검 과정에 달려 있습니다.  
결국, 가장 빠르게 혁신하는 방법은 가끔 멈춰 서서 지나온 길의 지뢰를 제거하는 것임을 잊지 마시기 바랍니다.
